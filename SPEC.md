# Gear Flow: доменная спецификация

## 1. Назначение

Gear Flow - система учета оборудования, мерча и расходников медиацентра.

В системе есть два режима учета:

- индивидуальный учет оборудования: камеры, микрофоны, ноутбуки, свет, объективы и другие вещи, которые нужно отслеживать поштучно;
- количественный учет мерча и расходников: ручки, стикеры, футболки, бейджи и другие взаимозаменяемые позиции.

Ядро системы должно хранить надежную физическую историю. Старые записи нельзя тихо редактировать, чтобы они совпали с реальностью. Если физический мир и цифровое состояние расходятся, система добавляет новое событие, которое объясняет исправление.

## 2. Базовые инварианты

Модель основана на `invariants.md`.

Кратко:

- У оборудования в любой момент есть ровно один активный ответственный держатель.
- Передача ответственности атомарна.
- История дописывается, а не переписывается.
- Исправления создаются отдельными событиями.
- Изменение состояния оборудования должно быть частью передачи или аудита. Корректирующее событие может менять состояние только если связано с передачей или аудитом.
- `Item_ID` используется только для индивидуально учитываемых объектов.
- Количественно учитываемые объекты не являются `Item`; они учитываются через `SKU`, `StockLot` и `Balance`.

## 3. Основные понятия

### 3.1 Holder

`Holder` - сущность, которая может быть ответственным держателем оборудования или держателем складского остатка.

Типы держателей:

- `person`: конкретный сотрудник, студент, волонтер или подрядчик;
- `location`: физическое место, например склад, студия, офис или площадка события;
- `external`: внешняя сторона, например ремонтная мастерская или партнер;
- `retired`: терминальный держатель для объектов, выведенных из активного оборота.

Оборудование не должно одновременно иметь и текущего человека, и текущее место как два равноправных поля ответственности. Активный `Holder` всегда один. Если дополнительно нужно знать физическое место или ответственного за место, это отдельная связь или метаданные, а не второй владелец объекта.

Подразделение в этой спецификации не является активным держателем первой версии. Под подразделением понимается команда или направление, например "видеопродакшн", "SMM", "студия подкастов" или "ивент-команда". Подразделение можно использовать как метку, фильтр или принадлежность человека/места, но конкретная ответственность за объект должна сводиться к человеку, месту или внешнему держателю.

Мероприятие в первой версии не является отдельной большой сущностью. Если нужно временно выдать оборудование или мерч на мероприятие, оно моделируется как временный `Holder` типа `location` с датами начала/окончания и понятным названием, например "День открытых дверей, площадка A".

Базовые места первой версии:

- `Студия`;
- `Склад`.

### 3.2 AssetItem

`AssetItem` - индивидуально учитываемый физический объект.

Обязательные поля:

- `item_id`: уникальный идентификатор и первичный ключ физической идентичности;
- `asset_type`: класс объекта, например камера, микрофон, объектив, ноутбук, штатив;
- `name`: человекочитаемое название;
- `status`: жизненный статус;
- `condition`: текущее физическое состояние;
- `created_at`;
- `created_by`;
- необязательные метаданные: серийный номер, модель, производитель, инвентарный номер, дата покупки, заметки.

Жизненные статусы:

- `active`: объект доступен для нормальной работы;
- `lost`: объект потерян или не найден после аудита/инцидента;
- `repair`: объект временно вне обычного использования из-за ремонта;
- `retired`: объект навсегда выведен из активного оборота;
- `disposed`: объект физически утилизирован или иначе выбыл.

Физические состояния:

- `working`: работает;
- `needs_attention`: требует внимания;
- `broken`: сломан;
- `unknown`: состояние неизвестно.

### 3.3 StockSKU

`StockSKU` - тип количественно учитываемой позиции.

Примеры:

- черная ручка;
- набор стикеров;
- черная футболка размера M;
- бейдж;
- блокнот.

Обязательные поля:

- `sku_id`: уникальный идентификатор SKU;
- `name`;
- `category`;
- `unit`: обычно `piece`, но может быть другая счетная единица;
- необязательные атрибуты: размер, цвет, дизайн, поставщик, кампания.

SKU не является идентичностью физического объекта. SKU описывает класс взаимозаменяемых единиц.

### 3.4 StockLot

`StockLot` - необязательная партия единиц SKU с общим происхождением или признаками.

Примеры:

- футболки из конкретного тиража;
- бейджи для конкретного мероприятия;
- ручки из конкретной поставки.

Обязательные поля:

- `lot_id`;
- `sku_id`;
- необязательные данные: дата поступления, источник, стоимость, кампания, срок годности, заметки.

Если для SKU не нужен учет партий, система может использовать партию по умолчанию.

Партии не обязательны для всего мерча. Для простых позиций можно вести учет без партии или через техническую партию по умолчанию. Для одежды, event-specific мерча или поставок, где важно происхождение, партия может быть включена.

### 3.5 StockBalance

`StockBalance` - проекция, а не источник истины.

Остаток рассчитывается из событий движения мерча/расходников.

Ключ баланса:

- `sku_id`;
- `lot_id`, если включен учет партий;
- `holder_id`.

Количество в балансе нельзя редактировать напрямую.

## 4. Модель событий

События только дописываются. Они являются основной исторической записью.

Общие поля события:

- `event_id`;
- `event_type`;
- `happened_at`: когда физическое действие или наблюдение произошло;
- `recorded_at`: когда событие внесли в систему;
- `recorded_by`;
- `reason`;
- `comment`;
- необязательные `evidence`: фото, документы, ссылки, листы аудита;
- необязательный `correction_of_event_id`, если событие исправляет предыдущее событие.

После создания событие неизменяемо. Если найдена ошибка, создается корректирующее событие.

## 5. События оборудования

### 5.1 AssetRegistered

Создает `AssetItem` и назначает начального держателя.

Обязательно:

- `item_id`;
- метаданные объекта;
- начальный `holder_id`;
- начальное `condition`.

Правила:

- `item_id` должен быть уникальным.
- Начальный держатель должен существовать.
- Регистрация является первым событием в цепочке объекта.

### 5.2 AssetTransferred

Передает ответственность за один или несколько объектов от одного держателя другому.

Обязательно:

- `item_ids`;
- `from_holder_id`;
- `to_holder_id`;
- необязательные наблюдения состояния по каждому объекту.

Правила:

- Каждый объект должен сейчас принадлежать `from_holder_id`.
- Передача всех объектов в событии проходит целиком или не проходит вообще.
- После события у каждого объекта есть ровно один активный держатель.
- Если состояние изменилось во время передачи, изменение состояния является частью этого события.

### 5.3 AssetAuditRecorded

Фиксирует физический аудит одного или нескольких объектов.

Обязательно:

- `scope`: держатель, место, список объектов, категория или произвольный набор аудита;
- наблюдаемые данные по объектам;
- аудитор;
- результат аудита.

Правила:

- Аудит может подтвердить совпадение цифрового состояния с физическим.
- Аудит может породить корректирующие события, если физическая реальность отличается от цифровой.
- Изменения состояния, найденные во время аудита, привязаны к событию аудита или к корректирующему событию, созданному из него.

### 5.4 AssetCorrectionRecorded

Исправляет текущее состояние объекта через добавление нового события.

Обязательно:

- `item_id`;
- исправленный держатель и/или состояние;
- причина;
- необязательный `correction_of_event_id`.

Правила:

- Событие не удаляет и не изменяет предыдущие события.
- Событие должно объяснять причину коррекции.
- Событие становится последним источником для соответствующей проекции.
- Если коррекция меняет физическое состояние объекта, она должна быть связана с аудитом или передачей. Быстрое физическое наблюдение состояния считается малым аудитом и должно оформляться через `AssetAuditRecorded`, а не как свободное изменение состояния.

### 5.5 AssetRetired

Выводит объект из активного оборота.

Обязательно:

- `item_id`;
- `from_holder_id`;
- причина вывода;
- финальный жизненный статус.

Правила:

- Объект должен сейчас принадлежать `from_holder_id`.
- Держателем объекта становится терминальный держатель, соответствующий жизненному статусу.
- Объекты в статусах `retired` или `disposed` нельзя снова передавать без явного события реактивации.

### 5.6 AssetReactivated

Возвращает объект из статуса `retired`, `lost` или `repair` в активный оборот.

Обязательно:

- `item_id`;
- `from_holder_id`;
- `to_holder_id`;
- состояние;
- причина.

Правила:

- Реактивация должна быть явной.
- Событие должно описывать физическое основание для реактивации.

## 6. События мерча и расходников

### 6.1 StockReceived

Добавляет количество на баланс держателя.

Обязательно:

- `sku_id`;
- необязательный `lot_id`;
- `to_holder_id`;
- `quantity`;
- источник или причина.

Правила:

- Количество должно быть положительным.
- SKU должен существовать до поступления.
- Партия должна существовать или создаваться как часть поступления.

### 6.2 StockMoved

Перемещает количество между держателями.

Обязательно:

- `sku_id`;
- необязательный `lot_id`;
- `from_holder_id`;
- `to_holder_id`;
- `quantity`.

Правила:

- Количество должно быть положительным.
- У источника должно быть достаточно количества.
- Списание у источника и зачисление получателю происходят атомарно.

### 6.3 StockIssued

Выдает мерч или расходники из инвентаря для потребления, раздачи, подарка, мероприятия или внешней передачи.

Обязательно:

- `sku_id`;
- необязательный `lot_id`;
- `from_holder_id`;
- `quantity`;
- цель выдачи;
- получатель или кампания, если известны.

Правила:

- Количество должно быть положительным.
- У источника должно быть достаточно количества.
- Выданный мерч не ожидается обратно.
- Если человек получает мерч "как подарок" или "осталось мало ручек, держите, разбирайте", это `StockIssued`.
- Если человек или команда временно забирает коробку мерча и позже может вернуть остаток, это `StockMoved` на временного держателя, место или мероприятие, а не `StockIssued`.

### 6.4 StockAuditRecorded

Фиксирует наблюдаемые количества по держателю, SKU или другому охвату аудита.

Обязательно:

- охват аудита;
- наблюдаемые количества;
- аудитор;
- результат аудита.

Правила:

- Аудит может подтвердить остатки.
- Аудит может создать события `StockAuditAdjusted` для расхождений.
- Остатки исправляются событиями, а не прямым редактированием.

### 6.5 StockAuditAdjusted

Корректирует остаток по результату физического аудита или проверенного исправления.

Обязательно:

- `sku_id`;
- необязательный `lot_id`;
- `holder_id`;
- знаковый `quantity_delta`;
- причина;
- необязательная ссылка на событие аудита.

Правила:

- Коррекция может быть положительной или отрицательной.
- Коррекция должна содержать причину.
- Итоговый остаток не должен стать отрицательным.

## 7. Команды

Команды - пользовательские операции, которые проверяют намерение и создают события.

### 7.1 Зарегистрировать оборудование

Создает объект и событие `AssetRegistered`.

Валидация:

- `item_id` уникален;
- начальный держатель существует;
- начальное состояние допустимо.

### 7.2 Передать оборудование

Создает событие `AssetTransferred`.

Валидация:

- все выбранные объекты существуют;
- все выбранные объекты сейчас находятся у `from_holder_id`;
- целевой держатель существует;
- объекты не выведены из оборота и не утилизированы.

### 7.3 Вернуть оборудование

Операционный вариант команды "Передать оборудование".

Обычно передает объект от человека или внешнего держателя обратно на склад или в студию.

### 7.4 Провести аудит оборудования

Создает `AssetAuditRecorded` и, при необходимости, корректирующие события.

Валидация:

- охват аудита допустим;
- наблюдения привязаны к конкретным `item_id`;
- изменения состояния привязаны к аудиту.

### 7.5 Зафиксировать состояние оборудования

Состояние нельзя менять отдельной свободной командой.

Допустимые пути:

- передача с наблюдением состояния;
- аудит с наблюдением состояния;
- коррекция, основанная на аудите или передаче. Проверенное физическое наблюдение состояния оформляется как аудит, пусть даже малый.

### 7.6 Вывести оборудование из оборота

Создает событие `AssetRetired`.

Валидация:

- объект существует;
- объект сейчас находится у указанного держателя;
- причина вывода заполнена.

### 7.7 Создать SKU

Создает карточку количественно учитываемой позиции.

Валидация:

- `sku_id` уникален;
- единица измерения допустима;
- категория заполнена.

### 7.8 Принять мерч или расходники

Создает событие `StockReceived`.

Валидация:

- SKU существует;
- держатель существует;
- количество положительное.

### 7.9 Переместить мерч или расходники

Создает событие `StockMoved`.

Валидация:

- SKU существует;
- источник и получатель существуют;
- количество положительное;
- у источника достаточно остатка.

### 7.10 Выдать мерч или расходники

Создает событие `StockIssued`.

Валидация:

- SKU существует;
- держатель существует;
- количество положительное;
- у источника достаточно остатка.

### 7.11 Провести аудит мерча или расходников

Создает `StockAuditRecorded` и, при необходимости, `StockAuditAdjusted`.

Валидация:

- охват аудита допустим;
- наблюдаемые количества неотрицательные;
- причины корректировок записаны.

### 7.12 Выдать оборудование по QR-коду

Быстрая операционная команда для сценария: человек сканирует QR-код на оборудовании телефоном и берет объект на себя.

Создает событие `AssetTransferred`.

QR-наклейка:

- печатается на обычном принтере;
- должна помещаться на минимальную поверхность уровня стандартной SD-карты;
- QR-код должен вести на короткую страницу объекта в локальной сети, например `/i/GF-000123`;
- `item_id` должен быть напечатан на наклейке читаемым текстом рядом с QR-кодом или под ним;
- если в QR-код зашить только `item_id`, обычная камера телефона не сможет сразу открыть страницу, поэтому для первой версии QR-код хранит короткую ссылку, содержащую `item_id`.

Пользовательский поток:

- человек сканирует QR-код обычной камерой телефона;
- открывается веб-страница объекта в локальной сети студии;
- человек выбирает себя из списка людей;
- вводит 4-значный PIN-код;
- указывает дату возврата;
- пишет свободным текстом причину взятия;
- при необходимости отмечает проблему с состоянием;
- если проблема отмечена, можно приложить фото с телефона.

Валидация:

- пользователь выбран из списка и подтвердил действие 4-значным PIN-кодом;
- QR-код связан с существующим `item_id`;
- объект доступен для передачи;
- текущий держатель объекта определяется из проекции;
- новым держателем становится выбранный пользователь;
- дата возврата заполнена;
- причина взятия заполнена;
- объект не находится в статусе `retired`, `disposed` или `lost`;
- текущий держатель допускает самообслуживаемую выдачу, например это склад, студия или другое место, откуда можно брать оборудование по QR-коду.

Правила:

- Сканирование не меняет историю напрямую, а создает обычное событие передачи.
- Если при сканировании человек отмечает проблему с состоянием, это состояние сохраняется как часть события передачи.
- Если объект физически найден у человека или в месте, которое не совпадает с цифровым текущим держателем, QR-сканирование не должно молча оформлять обычную передачу от цифрового держателя. Сначала нужно создать аудит/коррекцию расхождения, затем оформить новую передачу.
- Если объект сейчас числится за другим человеком или внешним держателем, самовыдача по QR-коду запрещена без отдельного подтверждения или корректирующего workflow.
- Если объект уже числится за другим человеком, обычный участник видит текущего держателя и может сообщить ответственному, но не может сам перехватить объект.
- Возврат можно реализовать симметрично: человек сканирует QR-код и выбирает место возврата.

### 7.13 Вернуть оборудование по QR-коду

Удобный интерфейсный сценарий над обычным `AssetTransferred`.

Пользовательский поток:

- человек сканирует QR-код оборудования;
- выбирает себя из списка людей;
- вводит 4-значный PIN-код;
- выбирает место возврата: `Студия` или `Склад`;
- при необходимости отмечает проблему с состоянием;
- если проблема отмечена, можно приложить фото.

Правила:

- Возврат не является отдельным доменным событием.
- Возврат создает обычный `AssetTransferred` от текущего держателя к выбранному месту.
- Если возвращающий пользователь не является текущим держателем, система должна показать расхождение и не оформлять молчаливую передачу без аудита/коррекции.

## 8. Проекции

Проекции - производные представления, рассчитанные из событий.

Обязательные проекции:

- текущий держатель оборудования по `item_id`;
- текущее состояние и жизненный статус оборудования;
- история конкретного объекта;
- все объекты у конкретного держателя;
- остатки мерча и расходников по SKU, партии и держателю;
- история движения мерча и расходников;
- отчет по расхождениям аудита;
- история корректировок.

Проекции должны быть восстановимы из журнала событий.

## 9. Правила валидации

### 9.1 Правила оборудования

- У объекта не может быть больше одного активного держателя.
- Передача оборудования должна быть атомарной.
- Изменение состояния оборудования должно быть частью передачи или аудита. Коррекция может менять состояние только если она связана с передачей или аудитом.
- История оборудования только дописывается.
- `item_id` нельзя переиспользовать.
- Объекты в статусах `retired` или `disposed` не должны показываться как доступные.

### 9.2 Правила мерча и расходников

- Количество меняется только через события.
- Остатки нельзя редактировать напрямую.
- Перемещение атомарно списывает количество у одного держателя и зачисляет другому.
- Количество должно быть положительным для поступления, перемещения и выдачи.
- Аудиторские корректировки могут быть положительными или отрицательными, но требуют причину.
- Отрицательные остатки в первой версии запрещены.

## 10. Права доступа

Для команды около 20 человек ролевая модель должна быть минимальной. Если для обычных действий нужны четыре разных ответственных человека, система будет тормозить работу.

Авторизация первой версии:

- человек выбирает себя из списка;
- вводит 4-значный PIN-код;
- PIN хранится только в виде хеша;
- сбросить PIN может только `admin`.

Админский вход:

- админ один;
- для админки достаточно отдельного админского пароля;
- админские действия не подтверждаются 4-значным PIN-кодом;
- PIN используется для быстрых действий участников, а не как полноценная защита админки.

Начальная ролевая модель:

- `admin`: управляет пользователями, справочниками, настройками и опасными административными действиями;
- `member`: берет и возвращает оборудование по QR-коду, смотрит состояние, участвует в обычных передачах;
- `inventory_manager`: ведет складские операции, регистрирует оборудование, принимает и выдает мерч, проводит аудиты и коррекции.

Права должны проверяться на уровне команд.

В первой версии лучше стремиться к самообслуживанию: большинство людей сами берут и возвращают оборудование через QR-код, а `inventory_manager` вмешивается только для складских операций, аудита, спорных случаев и первичной настройки.

## 11. Аудит и коррекции

Физическая реальность побеждает через добавление новых событий.

Если реальность отличается от цифрового состояния:

- записываем, что было обнаружено;
- по возможности ссылаемся на аудит или предыдущее событие;
- создаем корректирующее событие;
- сохраняем предыдущие события видимыми в истории.

Примеры:

- Камера физически найдена в Студии A, но в системе числится за Алексеем. Создаем аудит/коррекцию, которая меняет текущего держателя на Студию A.
- Микрофон вернули сломанным. Записываем передачу обратно на склад с состоянием `broken`.
- При пересчете найдено 93 набора стикеров, а цифровой остаток равен 100. Записываем аудит и `StockAuditAdjusted` с дельтой `-7`.

Возможные типы доказательств для аудита:

- текстовый комментарий;
- фото объекта, полки, коробки или места хранения;
- файл, например PDF, таблица или акт;
- ссылка на внешний документ;
- подпись или подтверждение участника;
- данные сканирования QR-кодов;
- геометка или устройство сканирования, если это будет нужно позже.

Для первой версии: обязательный текстовый комментарий для расхождений, опциональные фото и файлы, автоматическая фиксация факта QR-сканирования. Подписи, геометки и сложные акты откладываются.

## 12. Принятые решения

Принятые решения:

- Подразделение не является активным держателем первой версии. Ответственность сводится к человеку, месту или внешнему держателю.
- Выдача мерча человеку по умолчанию означает подарок, раздачу или потребление. Такой мерч не ожидается обратно.
- Отрицательные остатки запрещены.
- Для первой версии ремонта достаточно `external`-держателя и состояния объекта.
- QR-коды нужны в первой версии для выдачи и возврата оборудования.
- Партии мерча необязательны и используются только там, где есть практическая польза.
- Роли должны быть минимальными: `admin`, `member`, `inventory_manager`.
- Авторизация первой версии: выбор человека из списка и 4-значный PIN-код.
- Админ один, админка защищена отдельным паролем.
- PIN сбрасывает только `admin`.
- Базовые места хранения первой версии: `Студия` и `Склад`.
- Срок возврата задается датой, без обязательного времени.
- Причина взятия оборудования - свободный текст.
- Состояние при выдаче/возврате спрашивается только если человек хочет отметить проблему.
- При проблеме можно приложить фото с телефона.
- Нужно показывать экран просроченного оборудования.
- Первый релиз фокусируется на учете оборудования. Мерч остается в спецификации, но реализуется следующим срезом.
- Стек первой версии: Django, PostgreSQL, серверный HTML с HTMX там, где нужна интерактивность без тяжелого frontend.
- Нужна админская панель для людей, оборудования, QR-кодов и мест.
- QR-наклейки печатаются на обычном принтере; минимальный целевой размер должен помещаться на стандартную SD-карту.
- На наклейке печатается `item_id`; QR-код ведет на короткую URL-страницу объекта с этим `item_id`.
- Админка должна уметь печатать QR-наклейки по одной и пакетно: сразу для набора выбранных объектов или новых объектов.
- Макет наклейки первой версии минимальный: только QR-код и `item_id`, без названия предмета.
- Бэкапы PostgreSQL пишутся на внешний диск в отдельную папку.
- Бэкап выполняется каждый день в 03:00.
- Хранятся 3 последних бэкапа.
- Фото проблем хранятся файлами на сервере, в базе хранится ссылка.
- Экран просрочек видят только `inventory_manager` и `admin`.
- Экран просрочек показывает предмет, кто взял, дату возврата, причину и количество дней просрочки.
- Обязательные поля карточки оборудования: название, тип, начальное место.
- Доказательства аудита первой версии: комментарий обязателен для расхождений, фото и файлы опциональны, QR-сканы фиксируются автоматически.
- Возврат оборудования по QR-коду не требует отдельного доменного события. Это обычный `AssetTransferred` с удобным интерфейсом возврата.
- Мероприятие в первой версии моделируется как временный `Holder` типа `location`, а не как отдельная сущность.

## 13. Первый срез реализации

Минимальная полезная версия должна включать:

- админскую панель;
- управление людьми;
- управление местами;
- регистрацию оборудования;
- передачу оборудования;
- генерацию и печать QR-наклеек;
- выдачу и возврат оборудования по QR-коду;
- экран просроченного оборудования;
- аудит оборудования с коррекцией;
- фото проблемы при выдаче/возврате;
- read-only проекции текущего состояния оборудования.

Первый релиз должен сфокусироваться на оборудовании и QR-сценариях. Мерч и расходники остаются в модели, но могут быть реализованы вторым срезом после запуска оборудования.

## 14. Технический контекст первой версии

- Формат: веб-система.
- Размещение: локальная сеть студии.
- Протокол первой версии: HTTP.
- Хост: физический ПК на Windows 11.
- Серверная среда: Ubuntu Server в Hyper-V.
- База данных: PostgreSQL.
- Backend: Django.
- Frontend: серверный HTML, Django templates, HTMX для точечных интерактивных действий.
- Админка: Django admin плюс нужные внутренние страницы.
- Стартовые данные будут вводиться вручную, импорта на старте нет.
- Резервные копии PostgreSQL пишутся на внешний диск в отдельную папку.
- Расписание бэкапа: ежедневно в 03:00.
- Ротация бэкапов: хранить 3 последних.
